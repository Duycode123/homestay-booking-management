# Customer notification center

## Business goal

Give an authenticated customer one trusted place to review operational updates that already belong to their account, especially booking cancellation and refund progress.

## Actors

- Primary actor: authenticated customer
- Supporting actors: booking, payment, refund, support, and staff workflows that persist notifications

## Preconditions

- The actor has an enabled `account` record.
- The actor is authenticated and the security principal contains the account email.
- Notifications are persisted in `app_notification` with `recipient_id` equal to that account ID.

## Main flow

1. The customer opens the notification bell in the public header.
2. The frontend requests the newest notifications for the authenticated account.
3. The backend resolves the account from the authenticated email and returns only rows owned by that account.
4. Unread items are highlighted and counted on the bell.
5. Opening an item marks it as read and navigates to the relevant customer page.
6. The customer can open the full notification center, filter the list, or mark all notifications as read.

## Alternate and error flows

- If the account cannot be resolved, the backend rejects the request instead of returning another account's data.
- If a notification ID does not belong to the current account, the backend responds as not found.
- If loading fails, the UI keeps the previous state where possible and offers a retry action.
- If there are no notifications, the UI shows an explicit empty state rather than mock entries.

## Business rules

- Notification ownership is always enforced by `recipient_id`; IDs alone never authorize access.
- The API returns at most 50 newest items.
- Reading a notification does not resolve the underlying business task.
- `is_read` is presentation state; `is_resolved` remains workflow state.
- Refund, booking, payment, check-in, and check-out notifications link to booking history.
- Support and incident notifications link to customer support.

## Related endpoints

- `GET /api/notifications?limit=30`
- `PATCH /api/notifications/{id}/read`
- `PATCH /api/notifications/read-all?limit=30`

## Data touched

- `account`: resolve the authenticated actor.
- `app_notification`: list and update read state.

## Current implementation notes

- The backend is implemented under `backend.notification` with an inbound web adapter, application use case, outbound persistence port, and JDBC adapter.
- The customer header order is Favorites, Notifications, Account.
- The dropdown polls every 60 seconds while the application is open and refreshes immediately when opened.
- The full customer page is `/customer/notifications`.
- Existing cancellation and refund workflows already create persisted customer notifications and are displayed without mock data.

## Known gaps

- Notification production is not yet centralized for every booking/payment state transition.
- Scheduled stay reminders and review reminders are not currently generated by this use case.
- Real-time push uses polling; WebSocket or server-sent events can replace it later without changing the ownership rules or API result model.
